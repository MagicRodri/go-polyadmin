# Internationalisation

Every request is served in a locale resolved from the request itself.
Framework and host strings translate through one `Translator`; dates
and decimals format in the browser. English ships built in; French and
Russian ship as catalogs.

## What is translated, and what is not

Translated, wherever it appears in a page:

- Framework text — button labels, page titles, confirmation dialogs,
  filter labels, accessible names (`aria-label`, `placeholder`,
  `title`, `alt`), flash messages, validation errors, error pages.
- Host-declared text rendered through the framework's own templates —
  a field's `Label`/`HelpText`/`Placeholder`, a `Fieldset`'s `Title`/
  `Description`, a `Filter`'s label and choice labels, an `Action`'s
  label and confirm text, an `Inline`'s label, a custom page's nav
  label, a dashboard widget's title, the site title.

Never translated:

- Record values — whatever your `ModelAdmin` returns as field data.
- Object labels (breadcrumbs, relation links), email addresses, IDs,
  `Principal.DisplayName`.
- Table cells, chart points, activity/timeline entries — any widget
  data.
- Locale names in the switcher ("English", "Français", "Русский" are
  never run through the translator).

## Configuration

All optional; the zero value is English plus every catalog the
framework ships, resolved per request, switcher shown:

```go
core.WithDefaultLocale("en")        // default "en"
core.WithLocales("en", "fr")        // restrict; default = every locale with a catalog
core.WithLocaleResolver(func(request any, p *core.Principal) string { ... })
core.WithCatalogs(os.DirFS("locales")) // host catalogs, layered over the framework's
core.WithTranslator(t)              // replace the default Translator entirely
core.WithLocaleNames(map[string]string{"de": "Deutsch"})
core.WithoutLocaleSwitcher()        // hide the switcher, unmount its route
core.WithPseudoLocale()             // dev/test only: enables "en-XA"
```

`en` needs no catalog: its msgid *is* the English text. The supported
set is `en` plus every locale with a framework or host catalog,
intersected with `WithLocales` when given, plus `en-XA` when the
pseudo-locale is enabled. `WithTranslator` replaces the default
catalog-backed `Translator` outright — pair it with `WithLocales`,
since the admin can no longer ask a foreign translator what it
supports.

## How a request's locale is chosen

Resolved once per request, before any handler runs. First match wins:

1. The switcher cookie, `admin_locale` — the visitor's most recent
   explicit choice, if it still names a supported locale.
2. `WithLocaleResolver`, if configured. Its `principal` argument is
   `nil` on the login and error pages, since nothing is authenticated
   there yet; it's `nil` everywhere else, too, when no
   `Authenticator` is configured. An empty or unsupported result falls
   through to the next step. Authentication happens at most once per
   request even when both the locale resolver and the route's own
   authorization need the principal — the second lookup reuses the
   first's result. See [`authentication.md`](authentication.md).
3. `Accept-Language`, best match against the supported set, honouring
   q-values.
4. `DefaultLocale`.

Every candidate from steps 1–3 is matched the same way: an exact
locale wins, otherwise a regional variant maps onto its base language
(`fr-CA` → `fr`), and one language is never mapped onto another. The
pseudo-locale is never matched from `Accept-Language` — it has to be
chosen explicitly, by cookie or resolver.

The resolved locale drives everything in the request: the page and any
htmx fragment, flash messages set during it, validation errors, error
pages, `<html lang>`, and export column headers.

## The language switcher

A dropdown in the header (next to the theme toggle) and a compact one
on the login page, so a language can be picked before signing in.
Neither renders on error pages, and the whole thing — dropdown and
route — disappears when only one locale is supported or
`WithoutLocaleSwitcher()` is set.

Each option is its own name, never translated ("English", "Français",
"Русский"); built-in names cover `en`, `fr`, `ru` and `en-XA`, and
`WithLocaleNames` names anything else, falling back to the code
itself.

Choosing an option posts to `POST {base}/locale` (form field `locale`,
CSRF-protected like any other mutating route). A supported value sets
the `admin_locale` cookie (`Path` = the admin mount, `SameSite=Lax`,
`HttpOnly`, one year, `Secure` when the request is HTTPS) and redirects
back to wherever the visitor was, validated against the `Referer`; an
unsupported value sets nothing but still redirects.

A host that must force one language — company policy, a
single-tenant deployment — combines `WithoutLocaleSwitcher()` with a
`LocaleResolver` that always returns it.

## Translating your own strings

### Host catalogs

A `ModelAdmin`'s own text (labels, help text, action messages, ...)
isn't extracted into the framework's catalogs — it belongs in yours,
layered on top with `WithCatalogs`:

```go
core.WithCatalogs(os.DirFS("locales"))
```

One JSON file per locale at the filesystem root, `<locale>.json`,
keyed by the English text:

```json
{
  "Deactivate": "Désactiver",
  "%d record": {"one": "%d enregistrement", "other": "%d enregistrements"}
}
```

A value is either a plain string, or — for a msgid used with `tn`/
`core.TN` — an object of CLDR plural forms (`zero`, `one`, `two`,
`few`, `many`, `other`) keyed the same way the shipped `fr.json`/
`ru.json` are. A later `WithCatalogs` entry overrides an earlier one
(and the framework's own) for the same msgid, so a host catalog can
also reword the framework's strings — see below.

### In templates

```gotemplate
{{t "Save"}}
{{t "%s is required." .Label}}
{{tn "%d record" "%d records" .N .N}}
x-text="dark ? {{tjs "Light mode"}} : {{tjs "Dark mode"}}"
```

- `t "msgid" args...` — translated, then `fmt.Sprintf`'d only when
  `args` is non-empty. Placeholders are `fmt` verbs; use an explicit
  index (`%[2]s`) where a translation needs to reorder them.
- `tn "singular" "plural" n args...` — `n` picks the plural form,
  `args` fill the placeholders, so a count shown in the text is
  usually passed twice, as in the `%d record`/`%d records` example.
- `tjs "msgid" args...` — the same translation, JSON-encoded, for
  Alpine expressions inside an HTML attribute. A plain `{{t}}` inside
  a quoted JS string breaks on an apostrophe in the translation
  (`Mode d'affichage`); `tjs`'s JSON string literal survives the
  attribute's HTML escaping instead. Inside a `<script>` block, where
  there's no attribute escaping to survive, use `{{t}}` — it's already
  a quoted JS string there.
- A host string goes through the same functions with a non-literal
  argument: `{{t .Label}}`, `{{t $.Field.HelpText}}`.
- A whole sentence is one msgid — interpolate with a placeholder,
  never concatenate translated fragments: `{{t "Remove this %s?" (t
  $.Label)}}`, not `{{t "Remove this"}} {{t $.Label}}?`.
- A literal `%` in a msgid needs no escaping when `t`/`tn` is called
  with no `args`; it needs doubling (`%%`) only once the call takes
  arguments, same as `fmt.Sprintf`.

### In code

```go
core.T(ctx, "%s applied to %d record(s).", label, len(objects))
core.TN(ctx, "%d record", "%d records", n, n)
core.N_("Broadcast sent.") // marks a string for extraction without translating it yet
```

`core.Locale(ctx)` reads the resolved locale directly. `ctx` reaches
every `ModelAdmin` method, every `Validator`, and every custom
`AdminPage` handler (`core.PageContext.Locale()`) — see
[`model-admin.md`](model-admin.md#validation) and
[`routing.md`](routing.md#custom-admin-pages).

A string an action or validator returns is translated where the
framework uses it — an action's return value when it becomes a flash
message, a validator's `error` when the form re-renders — so a static
message only needs a host catalog entry, while an interpolated one is
translated by your own code with `core.T`:

```go
func validBalance(ctx context.Context, value any) error {
	if s, ok := value.(string); ok && s != "" {
		return errors.New("Enter a valid number.") // translated by the framework
	}
	return nil
}
```

Translating an already-translated string is harmless: it misses the
catalog (the text isn't the English msgid any more) and comes back
unchanged, so a validator is free to call `core.T` itself instead —
both styles compose.

## Rewording the framework's strings

Give a host catalog an entry keyed by the framework's own English
msgid, and it wins over the framework's translation for that locale
(the lookup order is: host catalog, then framework catalog, then the
English msgid itself):

```json
{ "Delete selected": "Remove checked items" }
```

## Dates and numbers

Formatting happens in the browser, not on the server, so there's no
server-side locale-formatting dependency.

- Date and datetime fields render as
  `<time datetime="2024-03-01" data-format="date">2024-03-01</time>`
  (or `data-format="datetime"`); `Decimal` fields render as
  `<span data-format="decimal" data-value="19.9">19.9</span>`.
  Integers render as-is — they're commonly IDs, years, or codes, where
  `1 234` would be wrong.
- A shared inline script in `theme.html` formats every such element
  with `Intl.DateTimeFormat`/`Intl.NumberFormat`, keyed off
  `document.documentElement.lang`, on load and after every htmx swap.
- Date-only values are formatted from their year/month/day components,
  never through `new Date("YYYY-MM-DD")` (which parses as UTC midnight
  and shows the previous day west of Greenwich). A datetime carrying an
  offset shows in the browser's own timezone; a naive one shows as
  wall-clock time, unconverted.
- Form inputs (`<input type="date">`, etc.) keep native ISO values;
  exports stay machine-readable. Without JavaScript, the ISO value
  shows as-is.
- The date picker's weekday and month names come from `Intl` with the
  page's own `lang`, not the browser's ambient locale.

The framework does not itself validate a date or a decimal typed into
a form field — a host validator does that, as `validFoundedDate` and
`validBalance` in `examples/fiber/organization_admin.go` show.

## The pseudo-locale

`WithPseudoLocale()` enables `en-XA`: not a catalog, but a wrapper
around the real translator. It translates as `en`, then accents the
letters and brackets the result — `Save` becomes `[Šàvé]` — leaving
`fmt` placeholders intact so the string still formats correctly.
Enable it in development or CI only; it exists to make an untranslated
string visible by inspection — any text on the page that isn't
bracketed and accented went out without passing through the
translator.

## Not supported

- **Right-to-left scripts.** `dir` is always `ltr`.
- **Server-side value formatting.** Dates and decimals are formatted
  in the browser (see above) — there's no server-side equivalent for a
  host that can't run JavaScript.
- **Translated URLs or slugs.** A resource's route is always its
  `Slug()`, in every locale.
